# コンテンツを非公開リポジトリへ分離し、毎日0時に自動公開する

- 状態：完了（mainへマージ済み。現状の仕様は[docs/specs/content-sync.md](../specs/content-sync.md)を参照）

## ユーザーストーリー

開発者として、ソースコードは公開したまま、記事の下書きをデプロイされるまで非公開のまま書き進めたい。それにより、書きかけのコンテンツが公開リポジトリ経由で誰でも読める状態をなくしたい。

## 背景（着手時の事実）

- コンテンツ（ページ・タグ・画像）は公開リポジトリの`apps/web/src/content/`と`src/assets/pages/`で管理されており、コミットした時点で公開されていた
- 既存コンテンツはすべてサイトで公開済みで、守る対象は「今後の下書き」
- 個人サイトで開発者は本人のみ。非公開リポジトリへアクセスできない環境（Pull requestのCIなど）ではコンテンツが空でよく、エラーで落ちないことだけが要件
- JSTは夏時間がないため、UTC固定のcronで定期実行の時刻が年中ずれない

## 価値（なぜやるか）

- 下書きを非公開のまま書き進め、公開のタイミングを「非公開リポジトリのmainへ載せるかどうか」で制御できる。
- 毎日0時（JST）の定期デプロイにより、「mainへpushしておけば翌0時すぎに公開される」予約公開の運用ができる。

成功の判定：公開リポジトリの追跡対象からコンテンツが消え、公開サイトの内容（URL・表示）が移行前後で変わらないこと。

## スコープ

### やること

- 全コンテンツの非公開リポジトリ`shikakun.com-content`（`pages/`・`tags/`・`assets/`）への移動
- ビルド・開発時に取り込むsyncの仕組み（CIとローカルで同一のスクリプト）
- push・毎日0時（JST）・手動の3トリガーでのデプロイ
- ローカル執筆時のホットリロードの維持

### やらないこと

- 既存コンテンツの本文・URL（slug）・デザインの変更
- faviconやbrand画像などページ以外の静的アセットの移動（公開のまま）
- 公開リポジトリのgit履歴からの過去コンテンツの削除（公開済みのため許容）

## 受け入れ条件（すべて達成済み）

- [x] 公開リポジトリのコンテンツディレクトリに追跡対象が存在しない（各ディレクトリの`.gitkeep`のみ）
- [x] 非公開リポジトリの`pages/`・`tags/`・`assets/`が、移行前と同じslug・表示でビルドに反映される（画像は`astro:assets`で最適化される）
- [x] 非公開コンテンツが公開リポジトリにcommitされない（`git check-ignore`で確認）
- [x] push・定期・手動の3トリガーでデプロイが走る（push: run 28060921170／手動: run 28061401830で検証済み）
- [x] 非公開リポジトリのmainへ新規ページをpushすると、翌0時すぎに公開される
- [x] 非公開リポジトリへアクセスできないCIでもビルドがエラーで落ちない
- [x] 認証情報は対象リポジトリ限定・読み取り専用（Deploy key）
- [x] コンテンツを増減しても公開リポジトリ側の設定変更（`.gitignore`の追記など）が不要
- [x] ローカルで`pnpm dev`だけで全ページが表示され、作業クローンの編集がホットリロードされる
- [x] コンテンツの取得に失敗しても、ローカルの既存ビルドツリーが壊れない（オフライン時は直前の状態を保つ）

## 採用した方針

- **sync**：追加依存なしのNodeスクリプト（`apps/web/scripts/sync-content.mjs`）。ソースは`CONTENT_SOURCE_DIR`→`CONTENT_REPO_URL`（shallow cloneのキャッシュ）→規約パス`../shikakun.com-content`の順で解決し、取得できたときだけ`.gitkeep`を除いてclean＋copyする（冪等・完全一致・失敗時は非破壊）。デプロイのみ`CONTENT_REQUIRED=true`で取得失敗をエラーにする
- **`.gitignore`**：コンテンツディレクトリを丸ごと無視して`.gitkeep`だけ追跡する。許可リストを持たないため、コンテンツの増減で設定変更が発生しない
- **認証**：非公開リポジトリに読み取り専用のDeploy keyを登録し、秘密鍵を公開リポジトリのActions secretへ置く（最小権限）
- **ホットリロード**：dev限定のAstro統合（`astro:server:setup`）でViteのwatcherに作業クローンを追加し、変更をsyncと同じコピー処理で反映する。コピーは一時ファイル経由のatomic write
- **カットオーバー**：公開リポジトリの変更を1ブランチにまとめ、非公開リポジトリとsecretを先に用意してから1回のマージでmainへ入れた

検討して不採用にした代替案：

- コレクションのloader baseを作業クローンへ向ける、またはsymlinkを張る方式。MDXの相対import（`../../components/...`・`../../assets/pages/...`）が実体側のパスで解決されて壊れるため不採用。コピー方式ならファイルがビルドツリーに実在するため、importがそのまま解決できる

## 作業の分割（実績）

1. mainに影響しない準備：非公開リポジトリの作成・コンテンツ移動・Deploy keyの登録
2. 公開リポジトリの変更を1ブランチで実施：sync・watcher・`.gitignore`・scripts・`deploy.yml`・コンテンツ削除
3. カットオーバー：まとめてマージし、手動デプロイ→push契機→翌0時の定期実行を順に確認

## リスクと軽減策（当時の判断）

| リスク | 対応 |
| --- | --- |
| 中間状態（コンテンツ削除済み・デプロイ未対応）で空サイトが本番公開される | 変更を1ブランチにまとめ、非公開リポジトリとsecretを先に用意してからマージした |
| mainへのcode pushで、その時点の未公開コンテンツも一緒に公開される | 合意済みの方針とした。公開まで伏せたいものは非公開リポジトリのmainへ載せない運用 |
| 壊れたfrontmatterで夜間の定期デプロイが失敗する | デプロイが失敗してもCloudflareは直前のデプロイを保持するため公開サイトは壊れない。失敗はGitHubのメール通知で検知する |
| git履歴に過去コンテンツが残る | すべて公開済みのコンテンツのため許容した |
