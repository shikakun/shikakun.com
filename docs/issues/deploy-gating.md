# テストを通過したコードだけが本番へデプロイされるようにする

- 状態：未着手
- 見積もり：M（1日以内）
- ブランチ：`deploy-gating`

## ユーザーストーリー

開発者として、CIの検査（lint・typecheck・テスト・ビルド）を通過したコードだけが本番へデプロイされるようにしたい。それにより、壊れたコードの公開を人の注意ではなく仕組みで防ぎたい。

## 背景（現状の事実）

- `deploy.yml`は`main`へのpushで起動し、lint・typecheck・テストを一切実行せずにビルド・デプロイする。`ci.yml`も同じpushで起動するが、両者は並行して独立に走るため、**CIが失敗するコミットでもデプロイは成功しうる**
- Pull request経由の変更はマージ前にCIで検証されるが、`main`への直接pushはこの検証を経ずにデプロイまで到達する
- `ci.yml`は`apps/web`をビルドしない（buildジョブの対象はdesign-tokens・react・Storybookのみ）。本番ビルド（`astro build`）の失敗は**デプロイ実行時まで検知されない**
- 緩和要因：デプロイが失敗した場合、Cloudflare側は直前のデプロイを保持するため公開中のサイトは壊れない。また`concurrency: group: deploy`で同時実行は直列化されている

## 価値（なぜやるか）

- テストが失敗する状態のコードが本番へ公開されることを防ぐ。現状は「pushする前にCIの結果を確認する」という運用に依存している。
- 本番ビルドの検証がCIに入ることで、ビルドを壊す変更にPull requestの段階で気づける。

成功の判定：CIの検査が失敗するコミットが本番へ到達しないこと。

## スコープ

### やること

- デプロイをCIの検査の成功にゲートする
- `apps/web`の本番ビルド（コンテンツが空の状態）をCIで検証する

### やらないこと

- ブランチ保護ルールなどGitHubリポジトリ設定の変更（ワークフローの変更で完結させる）
- Pull requestごとのプレビューデプロイ
- デプロイ後のスモークテスト（別の課題として検討する）

## 受け入れ条件

- [ ] CIのいずれかの検査（lint・typecheck・テスト・ビルド）が失敗するコミットは、`main`へpushされても本番へデプロイされない
- [ ] 検査がすべて成功した場合は、従来どおり自動でデプロイされる
- [ ] 定期実行（毎日0時JST）と手動実行（`workflow_dispatch`）のデプロイ経路が引き続き機能する
- [ ] `apps/web`の本番ビルドがCIで検証される（Pull requestのCIでも、コンテンツが空の状態でビルドが通ることの検証を兼ねる）
- [ ] デプロイの直列化（`concurrency: group: deploy`）が維持される

## 実装方針の選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| 1（推奨） | `ci.yml`と`deploy.yml`を1つのワークフローに統合し、デプロイジョブに`needs`で検査ジョブを指定する。デプロイジョブは`push`（main）・`schedule`・`workflow_dispatch`のときだけ実行する | コミットごとに検査とデプロイの関係がGitHubのUI上で追える。仕組みがもっとも単純 | 定期実行でも検査一式が走り、コンテンツ公開に数分余計にかかる |
| 2 | `ci.yml`を`workflow_call`の再利用可能ワークフローにし、`deploy.yml`が検査を呼び出してからデプロイする | ワークフローの責務分離を保てる | 設定が複雑になる。secretsの受け渡し（`secrets: inherit`）が必要 |
| 3 | `deploy.yml`のトリガーを`workflow_run`（CI完了後）へ変える | 既存ファイルの変更が最小 | 対象コミット（`head_sha`）の扱いが必要で、実行の連鎖がUI上で追いにくい。`schedule`との併用で構成が分かりにくくなる |

案1を推奨する。個人開発では見通しのよさを優先する。定期実行に検査時間が乗ることは、壊れたコードを公開しないことの対価として許容する（定期実行では直近のmainのコードが対象で、コード自体はマージ時に検証済みのため、実質はビルド検証の再確認になる）。

## 作業の分割

1. **CIにwebの本番ビルド検証を追加する**：この時点で単独の価値がある（Pull requestでビルド破壊に気づける）
2. **ワークフローを統合し、デプロイを`needs`でゲートする**：`concurrency`とデプロイ手順は現状のまま移す
3. **3経路の動作確認**：push・`workflow_dispatch`で実際に確認し、マージ後の初回定期実行を確認する

## リスクと軽減策

| リスク | 影響 | 軽減策 |
| --- | --- | --- |
| トリガー条件の書き誤り | デプロイが走らない、または意図せず走る | マージ前に`workflow_dispatch`で検証し、push・定期の実行ログを確認する |
| `schedule`はデフォルトブランチのワークフロー定義でのみ動く | 検証中のブランチでは定期実行を確認できない | マージ後の初回定期実行（翌0時）を確認する手順を作業に含める |
| CI時間の増加 | コンテンツの定期公開が数分遅れる | 許容する。問題になれば定期実行のみ軽量な検査に調整する |

## 完了の定義

受け入れ条件に加えて、このプロジェクト共通の完了条件を満たす。

- `pnpm lint`・`pnpm typecheck`・`pnpm test`・`pnpm build`が通る
- 仕様書（`docs/specs/ci-cd.md`）が実装後の事実と一致している
